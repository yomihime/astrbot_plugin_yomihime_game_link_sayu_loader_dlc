# Sayu 插件与 YGL 公共接口之间的缺口

对照基线为 GsCore 0.12.2 和 YGL Core 0.2.11。DLC 通过 `scopes.bind(ctx)` 确认当前命令，并在独立的插件数据库登记用户提交的 UID。私聊 `account` 命令也可以操作该用户的插件账号行。游戏服务的登录授权、全局账户清单及跨会话投递需要各自的权限。

Core 的独立候选在现有分派入口为前台保留容量，统一处理排队、执行期限及取消，并将可信聊天入口观察到的单聊或群聊类型传给命令。DLC 的 `account` 命令要求明确的单聊类型。[YGL Core Draft PR #34](https://github.com/yomihime/astrbot_plugin_yomihime_game_link/pull/34)

三个冻结模块的 `sources` 均为空。SDK 的 `scope.http.fetch` 要求已声明的来源，并拒绝模块传入 `Cookie` 或 `Authorization` 请求头。现有 Core 可在受限路径注入模块配置主体的凭据，但该主体不区分当前玩家、适配器和游戏账号。玩家凭据需要上表所述的逐账号、可撤销授权；未经该授权的私聊不应触发真实认证请求。

在独立临时数据库中，经 Core 的登录服务提交合成身份、取得逐玩家 grant 并通过私有读取授权后，当前公开 `scope.http.fetch` 仍未将该玩家的凭据发送给已声明来源。撤销后旧 scope 已不能继续读取。管理页面的来源授权提交到模块配置。正式 AstrBot 入口不接受外部事件自带 grant，也不会把玩家角色或服务签名交给模块。所需的是受信端从已认证主体选出有效 grant、验证游戏角色与请求用途，并在实际发包前重验。仅支持对固定 URL 发无参数 Bearer GET 的原型无法承接三款原包的账号请求。原神、星铁的记录请求使用 Cookie、角色参数、区服及相应签发信息；鸣潮使用另一组会话和设备字段。

鸣潮另有一个与凭据无关的缺口。原包查询出口 IP，将结果用于后续请求的设备字段。冻结包只允许公开静态资源。若增加匿名 HTTP 来源，应固定目标域和 GET 路径、禁用跳转和凭据注入，限制响应大小并校验返回的 IP。通过 Core 取得的是其配置的网络出口，代理设置可能使其与 worker 出口不同。新增来源时还需按当前包的信任策略检查来源权限。

候选 20 的原神武器材料回调还需要匿名动态查询。MiniGG 依次用名称、语言和等级查询资料，返回值参与原包的下一次请求。现有静态资源清单无法表达这条链路。可先验证经已声明来源调用 SDK 的 `scope.http.fetch`，再将经过约束的 GET 结果、HTTP 错误和取消送回发起请求的 worker。验收应观察这两次请求及回包，另测未经声明的主机、重定向和凭据头。是否需要扩展 Core 取决于现有 SDK 能否支持这次双向调用。

真实 WebChat 的测试、内存适配器的原生对照和只有源码定位的项目分别列在[整包对照记录](package-oracle.md)及[契约清单](plugin-contract.md)。原生在普通聊天中返回原始账户列表的行为与 YGL 的用户隔离要求有直接冲突，需要宿主产品决策。

### 已验证的玩家来源接口

独立 Core 分支提供 `accounts.confirm_player_login` 和 `scope.http.fetch_player`。受信宿主把一个私聊能力绑定到命名来源和固定 GET 路径；外部签发方核验后，Core 才为当前玩家保存可撤销凭据。隔离测试经真正的 CoreRuntime、独立 DLC、回环 TLS 与 SQLite，核对了两名玩家、错用途、重复确认、连接等待或响应期间撤销，以及写入密文后取消。这个分支的 79 项测试已通过。现场候选 22 使用的是调度分支。两个改动独立审查。[玩家授权草案 #35](https://github.com/yomihime/astrbot_plugin_yomihime_game_link/pull/35) · [调度草案 #34](https://github.com/yomihime/astrbot_plugin_yomihime_game_link/pull/34)

三个原包的账号请求仍有具体差异。原神、星铁的状态 GET 需要角色和区服查询参数、玩家 Cookie 及服务认可的请求证明；鸣潮获取角色列表需要 POST 表单及该玩家的访问与设备字段。固定 Bearer GET 在构建这些请求时就会拒绝，普通来源读取也无权注入上述玩家凭据。接入还需要由受信方确认角色、允许的方法、参数和凭据用途，并保留发送前撤销及响应交付检查。现场不具备这些能力。
